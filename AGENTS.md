# AGENTS.md — Contributor and AI Agent Guide

This document covers everything needed to work on `zackdell.com`: stack, design system, content conventions, and writing standards. The writing section is the most important part — read it before adding or editing any content.

---

## Stack

**Astro 5** static site, deploying via GitHub Actions to GitHub Pages from `dist/`. Branch: `feature/astro-rewrite`. Live at `zackdell.com`.

```
npm run dev      # localhost:4321
npm run check    # astro type-check
npm run build    # outputs dist/
```

Do **not** push `feature/astro-rewrite` directly. The deploy workflow triggers automatically on push and publishes to Pages.

## Design System

**Theme:** flight hardware / mission control. The aesthetic is defense-aerospace industrial: think instrument panels, PCB silkscreen, signal traces. Not literal space photography, not generic "dark mode SaaS."

### Color tokens (`src/styles/global.css :root`)

```
--bg0: #05070b       space-black page base
--bg1: #0c1017       raised surfaces
--bg2: #111725       cards
--line: rgba(148,163,184,0.12)   hairline borders
--accent: #e09456    PCB copper
--accent-2: #5fd1f9  signal cyan
--text: #e8edf4
--muted: #94a3b8
--font-display: 'Space Grotesk Variable'
--font-body: 'Inter Variable'
--font-mono: 'JetBrains Mono Variable'
```

Fonts installed via `@fontsource-variable/*`, imported in `Base.astro`. Background uses an engineering grid (48px) plus a sparse starfield on `body::before`.

### Project image SVGs

All SVG project images use `viewBox="0 0 1600 900"`. Background is `#05070b`. Copper (`#e09456`) and cyan (`#5fd1f9`) are the primary accent colors. Use `radialGradient` and `filter` for glow effects. A faint grid pattern (opacity ~0.03) adds texture. Monospace fonts for all labels. Each image should be specific to the project, not a generic placeholder.

## Writing Style

This is the most important section. Content on this site represents real engineering work. The writing should reflect that: direct, precise, and specific. It should read like something a competent engineer wrote, not something generated by prompting an AI to write resume bullets.

### Voice

Write as if explaining your work to another engineer at a whiteboard. You know what you built, why it was hard, and what tradeoffs you made. Lead with those things.

Confident, not boastful. Specific, not vague. Technical precision is good; jargon for its own sake is not.

### What to avoid

**Em-dashes.** Never use `—`. Use a period to end a clause, a colon to introduce, or restructure the sentence. No exceptions.

**Resume bullet openers.** Do not start highlights or body paragraphs with:
- "Designed and implemented..."
- "Built a X for Y to Z..."
- "Implemented a X using Y..."
- "Developed X to Y..."
- "Achieved measurable X..."
- "Handled the X challenges..."
- "Leveraging X to Y..."
- "Utilizing X..."
- "Ensuring X..."

These are filler. Lead with the technical subject or the interesting constraint instead.

**Gerund chains.** Avoid stacking gerunds: "enabling X, leveraging Y, achieving Z." Break them into sentences.

**Summarizing what you already said.** Do not end a section with "This demonstrates X" or "This approach ensures Y." If the writing is doing its job, it doesn't need a closing advertisement.

**Passive voice for things you built.** "A system was implemented..." is weak. Own what you built.

### Highlights (bullet points)

Highlights appear on the project detail page. They should be dense and specific. Lead with the technical fact, not the action verb:

Good:
- "Lock-free job queue on a fixed-size ring buffer; atomic head/tail pointers, no mutex on the dispatch path"
- "Firmware command interface reconstructed by capturing and analyzing Windows driver USB traffic, with no vendor documentation"
- "Sandboxed module system with explicit import declarations; one mod's globals cannot silently alias another's"

Not good:
- "Designed and implemented a lock-free job queue using a fixed-size ring buffer with atomic head/tail pointers, eliminating mutex contention on the hot dispatch path"
- "Implemented bytecode caching to reduce load times"
- "Achieved measurable throughput improvements"

Highlights should be readable standalone. Each one is one idea.

### Body copy (project and blog)

One idea per sentence. Introduce the problem or constraint before the solution. Short sentences are fine when making a clear point.

For project pages, the structure is typically:

1. **Opening paragraph:** what is this, what was the core challenge or constraint.
2. **Sections (H2):** one per major technical area. Each section leads with the interesting problem or decision, then the solution.
3. **No closing summary section.** The last section should be substantive content, not a recap.

For blog posts, write in the same voice. First-person is fine. Explain reasoning, not just outcomes. Show the thinking, not just the result.

### Descriptions and long_descriptions

`description` (card text): one punchy sentence. State what the project is and what makes it notable. No filler words, no trailing clauses.

`long_description` (page header): two to three sentences max. Context, scope, key technical fact. Still no em-dashes.

### Titles

Short. Descriptive. No subtitle syntax with colons or dashes. "Multithreaded Job System" not "Multithreaded Job System: A Deep Dive into Lock-Free Queues."

## Privacy Rules

These are hard constraints. Do not revert without explicit instruction.

- No phone number anywhere on the public site.
- No political organization affiliations anywhere public.
- `src/data/resume-data.json` is the public resume source; it must never contain a phone number.
- The AI Resume Tailor stays in `<details>` at the bottom of `resume.astro`. Do not move it or delete it.

## Component Contracts

- **ProjectCard** is a whole `<a>` tag. There is no inner "Details" button. Always pass `year` and `role` props.
- **TagFilter** reads tags from the content collection; no hardcoded tag lists.
- **ImageCarousel** accepts the `images[]` array from frontmatter; first image is shown on the card.
- Do not add inline styles for design tokens. Use CSS custom properties from `global.css`.
